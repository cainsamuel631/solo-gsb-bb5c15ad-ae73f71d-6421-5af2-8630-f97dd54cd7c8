# 舞台换景顺序优化

一个舞台演出换景顺序优化 Web 应用：录入不超过 **12 个场景**及其道具集合，设置**前后依赖**、**固定序位**、**禁止相邻**三类约束，系统自动计算满足全部约束且**道具增减次数最少**的演出顺序，并展示每次换景的道具增减明细。无解时会指出一组可复现的冲突约束。支持保存方案并随时重新载入编辑。

演出进行中还可以**演出中重排**：从一次求解结果确认已完成的连续前缀并录入当前舞台实际道具，系统锁定前缀、只重排剩余场景，并列展示原计划后缀与新后缀、成本增减与被舍弃场景；保存后可继续重排。

支持两种编排模式：

- **经典编排**：全部场景必须参演，仅最小化道具增减次数。
- **时长受限编排**：为每个场景设置**时长**、**必演**标记与**可选场景价值**，并指定**整场时长上限**。求解器从场景中选择一个包含全部必演项的子集参演（未入选场景不参与任何约束，固定序位按入选后的演出序列计算），**先最大化入选可选场景的价值总和，再最小化道具增减次数**，并展示入选 / 舍弃场景、已用 / 剩余时长与换景明细。必演场景已超时或不存在可行编排时给出对应无解提示。

## 快速开始（单条命令）

```bash
docker compose up --build
```

启动后访问：**http://localhost:3000**

> 依赖安装与数据目录初始化均随容器启动自动完成，无需额外步骤。
> 若使用旧版 Compose 插件，命令为 `docker-compose up --build`。

停止：`Ctrl+C` 或 `docker compose down`。保存的方案存放在名为 `plans-data` 的卷中，重启不丢失。

## 本地开发（不用 Docker）

```bash
npm install
npm start          # 访问 http://localhost:3000
npm test           # 运行求解器单元测试
```

要求 Node.js ≥ 18。方案数据默认保存在 `./data/plans.json`（可用环境变量 `DATA_DIR` 修改）。

## 功能说明

- **两种模式**：页面顶部可切换「经典编排」与「时长受限编排」。
- **场景与道具**：最多 12 个场景，每个场景一组道具（逗号分隔录入）。
- **时长受限编排附加字段**：
  - 时长 `duration`：非负整数（分钟）；
  - 必演 `required`：勾选后该场景必须入选（必演场景不参与可选价值统计）；
  - 可选价值 `value`：该场景入选时贡献的价值，仅对非必演场景生效；
  - 整场时长上限 `timeLimit`：入选场景总时长不得超过它。
- **约束**（未入选场景不参与约束；固定序位按入选后的演出序列计算）：
  - 前后依赖：场景 A 必须排在场景 B 之前；
  - 固定序位：某场景必须排在第 N 位；
  - 禁止相邻：两个场景不得紧挨着演出。
- **优化目标**：
  - 经典模式：`开场布置道具数 + 各次换景（撤下数 + 上台数）之和` 最小。
  - 时长受限模式：① 入选可选场景价值总和最大 → ② 道具增减次数最少 → ③ 同分保持确定顺序。
- **结果展示**：演出顺序、道具增减总次数与每次换景的撤下 / 上台明细；时长受限模式额外展示入选 / 舍弃场景清单、已用与剩余时长、入选价值。
- **无解分析**：
  - 经典模式：优先报告依赖环；否则给出一组极小冲突约束核心（去掉其中任意一条即恢复有解）。
  - 时长受限模式：必演场景总时长超限单独提示；必演项间的依赖环 / 固定序位等"结构性"冲突给出极小核心；若结构上可行但时长上限不足以插入缓冲场景，给出提高上限 / 放宽约束的建议。
- **方案管理**：保存、列表、载入重新编辑、删除；新字段（模式、时长上限、场景时长 / 必演 / 价值）随方案一起持久化，旧方案仍可正常载入（按经典模式处理）。

## 演出中重排

计算出结果后，页面下方出现「演出中重排」卡片：

1. 选择**已完成前 N 场**（必须是当前顺序从第 1 场开始的连续前缀，顺序不可改变，界面中以灰色锁定）；
2. 录入**当前舞台实际道具**（允许与计划不同——例如临时多留 / 提前上台的道具，默认按已完成末场的计划道具预填，可修改）；
3. 点击「只重排剩余场景」。

重排遵循的规则：

- **已完成顺序不可改变**，系统只优化剩余场景；
- **跨越前缀的依赖按完成事实校验**：已完成部分若存在反向依赖直接指出冲突；"剩余场景必须先于已完成场景"时，经典模式无解，时长受限模式下必演场景无解、可选场景**强制舍弃**并注明原因；
- **固定序位仍按整场绝对位次计算**（例如固定第 5 位，完成 3 场后它对应后缀第 2 位）；已完成场景实际位置与其固定位不符、或剩余场景被固定到前缀序位内 / 超出后缀长度时，指出具体冲突；
- 已完成末场与某剩余场景的**禁止相邻**会禁止该场景作为新后缀的首位；若因此锁死所有候选则给出边界冲突；
- **时长受限模式**：扣除前缀已用时长作为剩余预算，前缀已超时单独提示，剩余必演超时基于剩余预算提示；**已完成可选场景的价值与时长计入结果**，剩余选择继续按"价值优先、换景次数次优"；
- **首个剩余场景的换景代价从当前实际道具计算**（撤下台上多余道具 + 上台缺少道具），之后各次换景按场景道具集合计算；
- 结果**并列显示原计划后缀与新后缀**（各自的换景明细）、两者的**成本增减**（次），以及被舍弃 / 强制舍弃的场景；下方给出重排后的完整节目单。

**保存后可继续重排**：重排状态（已完成前缀、当前道具、最近一次重排结果）随方案一起持久化；方案列表中进行中的方案带 🎬 标记。载入后以重排后的完整节目单为基准，可以再确认新的已完成前缀、再次重排。

## 算法

场景数 n ≤ 12，均为子集动态规划（Held-Karp 风格），复杂度 `O(2^n · n²)`（12 个场景约 70 万状态），求解在毫秒级完成，结果保证全局最优且确定（同代价取下标字典序）。

- **经典模式**：状态 `(已排场景集合, 末尾场景)`，转移时校验前置依赖、固定序位与禁止相邻，代价为相邻场景道具集合的对称差大小。
- **时长受限模式**：单个全局子集 DP 同时求出**每个**入选子集的最优排列——利用"末尾场景在集合内无后继、其固定序位恰为集合长度 − 1"这一归纳刻画，使涉及未入选场景的约束自然失效；最后在含全部必演项且不超时的子集中按"价值最高 → 代价最低 → 掩码升序"择优。无解归因另用一次"必演必排、可选可作缓冲、不限时长"的结构可行性 DP 判断冲突是否可经提高上限解除。
- **演出中重排**：先按完成事实做前缀校验（依赖 / 固定绝对位次 / 前缀内相邻），再把剩余场景编译成同一个子集 DP 问题——固定位次平移为后缀位次、首位"开场布置代价"替换为"当前实际道具 → 该场景"的对称差、跨边界禁止相邻通过首位禁选掩码施加；时长受限模式以 `timeLimit − 前缀已用时长` 为预算、以 `前缀已获价值` 为价值保底，跨前缀依赖 / 固定位不可满足的可选场景在进入 DP 前强制舍弃。复杂度仍为 `O(2^n · n²)`。

## API 简介

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/solve` | 求解，body 为 `{ mode?, timeLimit?, scenes, constraints }` |
| POST | `/api/replan` | 演出中重排，body 额外含 `{ originalOrder, completedIds, currentProps }` |
| GET | `/api/plans` | 方案列表（进行中的方案带 `inProgress: true`） |
| POST | `/api/plans` | 新建方案（可带 `replan` 重排状态） |
| GET | `/api/plans/:id` | 读取方案 |
| PUT | `/api/plans/:id` | 更新方案（可带 `replan` 重排状态） |
| DELETE | `/api/plans/:id` | 删除方案 |

请求中 `mode` 取 `"classic"`（默认）或 `"timed"`；`timed` 时需提供正整数 `timeLimit`（分钟）。
经典模式场景形如 `{ id, name, props: [] }`；时长受限模式场景形如
`{ id, name, props: [], duration, required, value }`。约束形如
`{ dependencies: [{before, after}], fixedPositions: [{sceneId, position}], forbiddenAdjacencies: [{a, b}] }`。

### `/api/replan`

请求在求解 body 基础上增加：

- `originalOrder: string[]`：所依据的整场顺序（继续重排时传上一次重排返回的 `order`）；
- `completedIds: string[]`：已完成场景，按完成顺序排列，必须是 `originalOrder` 的连续前缀；
- `currentProps: string[]`：当前舞台上实际存在的道具。

成功响应（经典）主要字段：

```json
{
  "ok": true,
  "replanning": true,
  "prefixIds": ["A"],
  "suffixIds": ["C", "B"],
  "order": ["A", "C", "B"],
  "plannedSuffixIds": ["B", "C"],
  "newSteps": [ /* 从当前实际道具换入（rejoin）+ 后缀各次换景 */ ],
  "plannedSteps": [ /* 原计划后缀的换景明细，用于并列对比 */ ],
  "newSuffixCost": 4,
  "plannedSuffixCost": 5,
  "costDelta": -1,
  "currentProps": ["灯"]
}
```

时长受限模式额外返回 `prefixValue/suffixValue/totalValue`、`prefixDuration/suffixDuration/usedDuration/remainingDuration`、
`excludedIds`、`forcedOutIds`（跨前缀事实强制舍弃）、`forcedOutReasons` 与 `abandonedIds`（剩余选择中舍弃）。

前缀已违反约束 / 剩余必演或可选无法满足跨前缀约束时返回 `{ ok:false, conflict }`，
`conflict.type` 可能为 `prefix-violation`（完成事实冲突，含具体约束）、`boundary-adjacency`（末场禁邻锁死首位）、
`constraint-set` / `timed-infeasible`（后缀内部冲突）；前缀超时额外带 `"reason":"prefix-overtime"`，
剩余必演超预算带 `"reason":"required-overtime"`。

保存方案时 `replan` 形如：

```json
{ "completedIds": ["A"], "currentProps": ["灯"], "originalOrder": ["A","C","B"],
  "currentOrder": ["A","C","B"], "result": { /* 最近一次 /api/replan 响应，可选 */ } }
```

`timed` 模式成功响应示例字段：

```json
{
  "ok": true,
  "mode": "timed",
  "order": ["C", "A"],
  "selectedIds": ["C", "A"],
  "excludedIds": ["B"],
  "totalCost": 3,
  "totalValue": 8,
  "usedDuration": 20,
  "remainingDuration": 0,
  "timeLimit": 20,
  "steps": [ /* 开场布置与每次换景的撤下/上台明细 */ ]
}
```

无解时返回 `{ ok:false, conflict }`；必演超时时额外带 `"reason":"required-overtime"`，
`conflict.type` 为 `required-overtime` / `dependency-cycle` / `constraint-set` / `timed-infeasible` 之一。
